# Informe de Análisis Defensivo de Seguridad Web
**Objetivo:** Mejorar la postura de seguridad del entorno de laboratorio OWASP Juice Shop basándose estrictamente en los hallazgos automatizados del escaneo de OWASP ZAP proporcionados.

---

### 1. Resumen ejecutivo
El presente informe analiza los resultados obtenidos de un escaneo automatizado realizado con OWASP ZAP sobre OWASP Juice Shop. El análisis identifica un total de 14 tipos de alertas, clasificadas en niveles de riesgo **Medio (Medium/High)**, **Bajo (Low)** e **Informacional**. 

Es importante destacar que **ninguno de los hallazgos automatizados constituye por sí solo una vulnerabilidad confirmada o explotada**, sino que representan indicadores de posibles debilidades de configuración, falta de endurecimiento (hardening) o áreas que requieren una validación manual profunda. Abordar estos puntos permitirá reducir la superficie de ataque y alinear la aplicación con las buenas prácticas de desarrollo seguro.

---

### 2. Hallazgos prioritarios y por qué importan

Los hallazgos de riesgo **Medio** representan las áreas de mayor atención identificadas en este informe:

*   **Backup File Disclosure (Riesgo: Medio, 31 instancias):** 
    *   *Por qué importa:* Indica que el servidor web podría estar exponiendo copias de seguridad de archivos. Esto es crítico porque las copias de seguridad a menudo contienen código fuente, credenciales de bases de datos o lógica interna de la aplicación que un atacante podría usar para comprometer el sistema.
*   **Bypassing 403 (Riesgo: Medio, 6 instancias):** 
    *   *Por qué importa:* El escáner detectó respuestas con código 200 (éxito) al enviar payloads diseñados para saltarse restricciones de acceso. Esto sugiere que las políticas de control de acceso en ciertos endpoints podrían ser eludidas mediante manipulación de peticiones, exponiendo recursos restringidos.
*   **CORS Misconfiguration / Cross-Domain Misconfiguration (Riesgo: Medio, 5 instancias cada uno):** 
    *   *Por qué importa:* Una mala configuración en el Intercambio de Recursos de Origen Cruzado (CORS) puede permitir que sitios web maliciosos lean datos sensibles de los usuarios mediante consultas AJAX autorizadas o no autorizadas, rompiendo la política de mismo origen (SOP).
*   **Content Security Policy (CSP) Header Not Set (Riesgo: Medio, 5 instancias):** 
    *   *Por qué importa:* La ausencia de una cabecera CSP debilita la capacidad de la aplicación para mitigar ataques de inyección de código, especialmente Cross-Site Scripting (XSS), al no restringir desde dónde se pueden cargar recursos como JavaScript, CSS o imágenes.

### 3. Recomendaciones de corrección concretas y ordenadas por prioridad

Se establece el siguiente orden de prioridad para mitigar los riesgos detectados:

1.  **Prioridad Alta (Mitigación de Riesgos Medios):**
    *   **Eliminar archivos de respaldo:** Asegurar que los procesos de despliegue no dejen archivos de respaldo (`.bak`, copias ocultas, etc.) en la raíz del servidor web o directorios accesibles públicamente.
    *   **Revisar Controles de Acceso (Bypassing 403):** Auditar la lógica de enrutamiento y los proxies inversos o servidores web para garantizar que la normalización de rutas y las restricciones de autorización (códigos 403) se apliquen de forma consistente y no puedan evadirse.
    *   **Endurecer CORS:** Configurar estrictamente la cabecera `Access-Control-Allow-Origin` para permitir únicamente dominios legítimos y necesarios, evitando comodines (`*`) o confíar ciegamente en el origen proporcionado por el cliente cuando se maneja información sensible.
    *   **Implementar Content Security Policy (CSP):** Configurar el servidor web o la aplicación para enviar una cabecera `Content-Security-Policy` robusta que limite los orígenes permitidos para scripts, estilos y otros recursos.

2.  **Prioridad Media (Endurecimiento y Buenas Prácticas - Riesgo Bajo):**
    *   **Actualizar Políticas de Seguridad del Navegador:** 
        *   Implementar o corregir las cabeceras `Cross-Origin-Embedder-Policy` (COEP) y `Cross-Origin-Opener-Policy` (COOP).
        *   Reemplazar la cabecera obsoleta `Feature-Policy` por la estándar actual `Permissions-Policy`.
    *   **Revisión de Código y Funciones:** Inspeccionar el uso de funciones JavaScript marcadas como potencialmente peligrosas para asegurar que no introduzcan vectores de inyección o XSS.

3.  **Prioridad Baja (Informacional y Optimización):**
    *   Evaluar el manejo de caché (`Storable and Cacheable Content`) en páginas que contengan información sensible o específica de usuario, implementando cabeceras como `Cache-Control: no-store` cuando sea necesario.

### 4. Qué debería comprobarse manualmente para validar cada hallazgo

Dado que las herramientas automatizadas generan alertas basadas en heurísticas, se deben realizar las siguientes validaciones manuales:

*   **Para *Backup File Disclosure*:** Intentar acceder directamente a las URLs reportadas mediante un navegador o cliente HTTP (como curl/Burp Suite) para verificar si el contenido devuelto corresponde efectivamente a un archivo de respaldo con información sensible y no a un falso positivo derivado de una regla de enrutamiento personalizada (ej. un error 404 personalizado que responde con código 200).
*   **Para *Bypassing 403*:** Reproducir la petición HTTP original que devolvió 403 y comparar la respuesta con la obtenida al aplicar el payload de ZAP. Verificar si el recurso al que se accedió realmente contiene información protegida o si es una ruta inexistente.
*   **Para *CORS Misconfiguration*:** Enviar una petición HTTP maliciosa con una cabecera `Origin: https://attacker.com` y comprobar si el servidor responde reflejando dicho origen en `Access-Control-Allow-Origin` junto con `Access-Control-Allow-Credentials: true`.
*   **Para *CSP Header Not Set*:** Inspeccionar las respuestas HTTP de las páginas principales utilizando las herramientas de desarrollo del navegador para confirmar la ausencia total de la cabecera `Content-Security-Policy`.
*   **Para *Timestamp Disclosure* y *Dangerous JS Functions*:** Realizar una revisión estática del código fuente (Code Review) para determinar si los timestamps expuestos tienen repercusión en la seguridad y si las funciones de JavaScript analizadas procesan datos controlados por el usuario sin la debida sanitización.

---

### 5. Limitaciones del análisis y falsos positivos posibles

*   **Naturaleza del escaneo automatizado:** Este informe se basa exclusivamente en los datos de salida proporcionados por un escáner automatizado (OWASP ZAP). Las herramientas automáticas no comprenden el contexto de negocio de la aplicación ni la lógica interna.
*   **Posibles Falsos Positivos:** 
    *   *Backup File Disclosure / Bypassing 403:* Aplicaciones modernas de una sola página (SPA) como OWASP Juice Shop a menudo devuelven códigos de estado HTTP personalizados (por ejemplo, redirigir al enrutador de cliente devolviendo un código 200 en lugar de un 404 o 403 real), lo que puede confundir al escáner y generar falsas alertas de divulgación o bypass.
    *   *CORS:* Algunas configuraciones de CORS pueden ser intencionales para permitir el funcionamiento de APIs públicas o recursos estáticos compartidos dentro del laboratorio, por lo que su criticidad debe evaluarse según la sensibilidad de los datos expuestos.
*   **Ausencia de alertas no implica seguridad:** Si alguna vulnerabilidad específica no aparece listada en este informe, **no significa que la aplicación esté libre de ella**, sino únicamente que el escáner ZAP no la detectó o no fue configurado para evaluarla en esta ejecución particular.

Este análisis es orientativo. Valida los hallazgos manualmente antes de tomar decisiones.
